# Known Limitations

Honest, current limitations. Updated as the implementation evolves. Anything not listed as implemented in the README is not implemented.

## Scope and evidence

- **Synthetic only.** All repositories, failures, traces and logs are generated by `synthetic-labs/monorepo-build`. No real user data is used.
- **No benchmark claims.** Token and cost figures come from a deterministic provider (`synthetic`) or documented estimators (`estimated`). They demonstrate the mechanism on a synthetic corpus; they are not evidence of general savings.
- **One task family.** The proof of concept covers monorepo build failures (three fault kinds). Additional families are P2.

## Compiler

- The Reflex Compiler **selects and parameterizes operators from a typed library** and validates them against recorded traces. It does not synthesize new code.
- Traces must carry harness-provided semantic annotations (`purpose`/`intent`). Unannotated live traces would need an annotator (roadmap).
- Fingerprinting is rule- and feature-based (no embeddings).

## Execution and safety

- **Application-level containment only.** Commands use structured arguments, allowlists, confined working directories, scrubbed environments, timeouts and output caps. This is not an OS-level sandbox; there is no network namespace, seccomp, or cgroup enforcement.
- Container isolation is available through the provided Dockerfile but is not a validated security boundary.

## Providers

- **Deterministic provider is not a model.** It is a scripted policy that stands in for one so the demo runs offline.
- **Live mode** (Azure OpenAI / OpenAI-compatible) is optional. Adapters are validated against a local protocol stub only, unless `docs/VALIDATION_LEDGER.md` records a live smoke test.

## Persistence and scale

- SQLite, single node. Audit history is append-only (trigger-enforced) and hash-chained, so it is tamper-evident at the application/database level; it is not WORM storage.
- Demo Reset recreates the database and starts a new audit chain that records the previous chain head.

## Azure

- Bicep templates, workflows and adapters are provided and validated locally (`bicep build`, what-if where possible). **No Azure resources are claimed to be deployed** unless the ledger records a successful deployment and smoke test.
